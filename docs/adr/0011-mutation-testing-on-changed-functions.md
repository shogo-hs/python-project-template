# ADR 0011: ミューテーションテストの範囲を PR で中身を変えた関数に絞り、時間の上限を付ける

最終更新: 2026-11-25
- ステータス: 承認済み(accepted)
- 決定者: shogo-hs
- 関連: [ADR 0010](./0010-mutation-testing-on-changed-modules.md)（変異を入れる範囲を置き換える。ほかの決定は引き継ぐ）, [ADR 0007](./0007-review-relation-diff-and-complexity-gate.md)

## 1. 文脈

- ADR 0010 は、PR で変えた `src/` のモジュールに変異を入れると決め、「ジョブが 10 分を超えるようなら、関数の単位に絞る」をフォローアップに残した。
- テンプレート v1.2.0 を取り込んだ relkb（src 約 3,000 行、テスト 249 本。テストは本物の組み込み DB と git を動かす）の PR で測った（2026-11-25）。
  - 測った事実: 変えた src のモジュールは 13 個で、そこに入る変異は 2,496 個だった（多い順に 825・430・283・205・194・100・94・93・91・80・79・22。残りの 1 個は 0）。CI の `mutation` ジョブは 26 分たっても終わらず、打ち切った。手元（Raspberry Pi 5、子プロセス 2 本）では、変異 1 個あたり約 0.5 秒だった（軽いモジュール 6 つの 515 個に 4 分半）。
  - 見込み: 最後まで流すと 30 分〜1 時間かかる。push のたびに走り直すので、非公開リポジトリの GitHub Actions の利用枠を大きく使う。
  - 825 個のモジュールは、その PR では関数を 5 つ足して 1 つを少し直しただけだった。残りは PR と関係の無い関数の変異になる。
- mutmut 3.8.1 が変異を入れるのは、モジュール直下の関数と、モジュール直下のクラスのメソッドだけ（mutmut のソースを読み、生成したサンプルで流して確かめた）。関数の中の関数は外側の関数の変異になる。クラスの中のクラスのメソッド、`if` / `try` の中の関数、デコレーター付きの関数（`@staticmethod` / `@classmethod` が 1 つだけのものを除く）には入れない。変異の名前は `<モジュール>.x_<関数>__mutmut_N` か `<モジュール>.xǁ<クラス>ǁ<メソッド>__mutmut_N` で、`mutmut run` は名前のパターンで絞れる。
- `tools/code_graph.py` が出す「変わった定義」（ADR 0010 のフォローアップが使うとしていたもの）は、増えた・消えた・引数や戻り値の型が変わった定義だけで、本体だけを変えた関数を拾えない。

## 2. 決定

- 変異を入れる範囲を、PR で中身を変えた関数・メソッドに絞る。`tools/changed_functions.py` が、PR の merge commit（head）とその第 1 親（base）の `src/` を比べ、mutmut が変異を入れる範囲の関数のうち、base に無いか構文木（`ast.dump`）が違うものを、mutmut の名前で出す。`mutation` ジョブは、その名前に `__mutmut_*` を付けたパターンだけを `mutmut run` に渡す。
- 変異を流すステップに時間の上限を付ける。`ci.yml` の先頭の `MUTATION_TIMEOUT_MINUTES`（既定は 15 分）を `timeout` に渡す。上限で打ち切っても CI は落とさず、そこまでに確かめた分の生き残りと、確かめていない変異の数・関数をコメントに出す。残りは手元で流す。
- コメントに、中身を変えた関数の数・変異が入った関数の数・変異の数・生き残りの数・呼ぶテストが無くて確かめられなかった変異の数を出す。
- ADR 0010 のほかの決定（mutmut を使う、生き残りで CI を落とさない、テストの規約）は変えない。
- 判断の基準として、次の 3 つを優先した。1 つ目は、PR ごとの時間を変更の大きさに比例させ、上を決めること。2 つ目は、コメントに出る生き残りを、その PR で書いた・直したコードのものにすること。3 つ目は、絞り方を mutmut と同じ単位・同じ比べ方にして、足すコードを小さくすること（mutmut も、前回の結果を使い回すかを関数ごとの構文木のハッシュで決めている）。

## 3. 代替案と不採用理由

- 代替案A: 差分の行（`git diff -U0` の新しい側の行番号）が、head の関数の行の範囲（`lineno`〜`end_lineno`）に入るかで決める。
  - 不採用理由: 関数の中の行を消しただけの変更は、新しい側に行が無いので、別の扱いが要る。コメント・空行・整形だけの変更でも、その関数の変異を全部流すことになる。構文木を比べるなら、どちらも起きず、差分の形式を読むコードも要らない。
- 代替案B: `tools/code_graph.py` の「変わった定義」を使う（ADR 0010 のフォローアップの案）。
  - 不採用理由: 本体だけを変えた関数を拾えない。定義の範囲も mutmut と違う（`if` / `try` の中の定義とクラスの中のクラスを含む）。本体の比較を足すと、レビュー用の差分を作るスクリプトに mutmut の名前の決まりが混ざる。
- 代替案C: 範囲はモジュールのまま、時間の上限だけを付ける。
  - 不採用理由: PR と関係の無い関数の変異で上限を使い切り、変えた関数に届かないことがある。relkb の PR では、2,496 個のうち変えた関数の変異は 1,300 個だった。
- 代替案D: 時間の上限を、ジョブかステップの `timeout-minutes` で付ける。
  - 不採用理由: 超えるとステップが失敗になり、そこまでに確かめた分のコメントが出ない。`timeout` コマンドなら、同じステップの中で続きを作れる。
- 代替案E: docstring だけを変えた関数を外す。
  - 不採用理由: relkb の PR では、変えた関数 50 個のうち docstring だけの変更は 2 個だった。外すコードを足すほどの差が無い。
- 代替案F: 変えた関数を呼ぶ関数や、変えたテストが通る関数にも変異を入れる。
  - 不採用理由: 呼び出しの解決は名前での近似しか無く（ADR 0007）、範囲が読めなくなる。必要なら手元でモジュールを指定して流せる。

## 4. 影響

- コードへの影響: `project/tools/changed_functions.py` と `project/tests/tools/test_changed_functions.py` を足す。`project/.github/workflows/ci.yml` の `mutation` ジョブを書き換える。既存のプロジェクトは、テンプレートの更新を取り込むと次の PR から変わる。
- 出なくなるもの: 触ったモジュールの、変えていない関数に前からある生き残り（ADR 0010 では出ていた）。モジュール直下の定数やクラスの属性だけを変えた PR では、変異を流さない（mutmut はもともと関数の外に変異を入れない）。テストだけを変えた PR で流さないのは、これまでと同じ。
- 運用への影響: 上限の時間には、mutmut の準備（テスト全体を 1 周流して、どのテストがどの関数を通るかを調べる）も入る。テスト全体が上限より長いプロジェクトでは 1 個も確かめられないので、`MUTATION_TIMEOUT_MINUTES` を上げる。変異を流すのは上限までで、そのあとに結果の読み出しと生き残りの差分の表示（1 個に 1 秒弱）が続く。打ち切りが mutmut の結果の書き込みと重なると結果のファイルが読めなくなるので、そのときも落とさず、読めなかったことをコメントに書く。
- 実測（Raspberry Pi 5、子プロセス 2 本）: 生成したサンプルで関数を 1 つだけ変えると、モジュールの変異 34 個のうち、その関数の 4 個だけが流れた（ステップ全体で 8 秒）。上限を 15 秒にして関数を 7 個変えると、変異 26 個のうち 18 個を残して打ち切り、ステップは落ちず、確かめていない 18 個とその関数がコメントに出た。
- relkb の PR での実測（同じ機械。PR の merge commit を手元で作り、ジョブのステップをそのまま流した）: 中身を変えた関数は 50 個（変えた 13 モジュールの関数 115 個のうち）で、変異は 2,496 個から 1,300 個に減った（825 個のモジュールは 188 個）。準備は 1 分あまりで終わり、上限の 15 分で打ち切られた。確かめたのは 909 個（生き残り 61 個）で、391 個が残った。ステップ全体は 951 秒だった。この PR は関数を 50 個変える大きさなので、関数に絞っても半分にしかならず、ジョブの時間を決めるのは上限のほうになる。GitHub Actions の速さでは測っていない。
- ドキュメントへの影響: `project/AGENTS.md`（テストの節）、`project/README.md.jinja`（よく使うコマンド・構成）、PR テンプレートのチェックリスト、根の `README.md`、ADR 0010（関連と変更履歴）。

## 5. フォローアップ

- relkb にこの版を取り込み、PR ごとの `mutation` ジョブの時間と、時間切れの回数を見る。大きい PR で時間切れが続くようなら、変えた行に当たる変異だけに絞れないかを調べる（mutmut に行で絞る機能は無い。`mutmut show` の差分から変異の行を求められるかは確かめていない）。
- ADR 0010 のフォローアップの 1 つ目（直さなくてよい生き残りの割合を数える）は続ける。
