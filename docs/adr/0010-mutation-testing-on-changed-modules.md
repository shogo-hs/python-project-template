# ADR 0010: PR で変えたモジュールにミューテーションテストをかけ、生き残りを PR にコメントする

最終更新: 2026-11-25
- ステータス: 承認済み(accepted)
- 決定者: shogo-hs
- 関連: [ADR 0003](./0003-expand-ci-quality-gates.md), [ADR 0007](./0007-review-relation-diff-and-complexity-gate.md), [ADR 0011](./0011-mutation-testing-on-changed-functions.md)（変異を入れる範囲を置き換えた）

## 1. 文脈

- AI のエージェントは、呼ぶだけのテストや `is not None` だけを確かめるテストを量産しがちになる。カバレッジの門（80%）は、テストが行を通ったかしか見ないので、こうしたテストでも通る。
- ミューテーションテストは、コードをわざと壊した版（変異。`>=` を `>` にする、`[:3]` を `[:4]` にする、など）を作り、テストがそれを落とせるかを見る。落とせなかった変異（生き残り）は、テストが確かめていない振る舞いを指す。
- 生成したサンプルで実測した（Raspberry Pi 5、Python 3.14.3、mutmut 3.8.1）。10 個以上で 1 割引く関数を、値を確かめないテストで呼ぶと、カバレッジは 100% のまま、変異 8 個のうち 7 個が生き残った。値を確かめるテストにすると 8 個とも落ちた。
- 全体にかけると重く、生き残りには直さなくてよいものも混ざる。relkb（src 2,785 行、テスト 135 本）に全体でかけると、変異は 2,423 個で、25 分で 2,319 個まで進んだところで打ち切った。その時点の生き残りは 273 個だった。そこから等間隔に 11 個を取り出して見ると、テストの穴（並び順の `reverse=True` を消す、件数の上限を変える、など）が 6 個だった。残りは、文言だけの変化（help の文を消す、など）が 3 個、結果の変わらない書き換え（`False` を `None` にする）が 2 個だった。モジュールを 1 つに絞ると 55 秒で終わった。
- Google は、変えた行だけをレビューのときに変異させ、生き残りをレビューの指摘として出している。作者は、指摘を解決しないままでも提出できる。リポジトリ全体のスコアは、行動につながらないので使っていない（Petrović ほか、Practical Mutation Testing at Scale、arXiv 2102.11378）。

## 2. 決定

- dev 依存に mutmut（3.8.1 以上。pytest 9.2 に対応したのは 3.8.1 から）を足し、`pyproject.toml` の `[tool.mutmut]` に設定を書く。mutmut は `mutants/` にコピーを作ってテストを流すので、`tests/tools` が読む `tools/` もコピーさせる。カバレッジの門は、mutmut の中では外す（`--no-cov`）。`mutants/` は `.gitignore` と mypy の対象から外す。
- CI に `mutation` ジョブを足す。PR の merge commit とその第 1 親の差分から、変えた `src/` のモジュールを出し、そのモジュールの変異だけを流す。生き残りは、変異ごとの差分を PR にコメントする。同じ PR への 2 回目以降は、前のコメントを上書きする。
- 生き残りがあっても CI は落とさない。mutmut の準備（テストの収集など）が失敗したときだけ落とす。
- `project/AGENTS.md` に、テストの規約を書く。テストは振る舞いを値で確かめる。条件・境界・戻り値・順序が変わる生き残りにはテストを足す。文言だけの変化や結果の変わらない書き換えは残してよく、生き残りを減らすためだけのテストは書かない。
- 判断の基準として、次の 3 つを優先した。1 つ目は、エージェントが書いたテストの穴を、人がテストを読まずに PR で見られること。2 つ目は、意味の無いテストを書く動機を新しく作らないこと。3 つ目は、PR ごとの時間を変更の大きさに比例させること。

## 3. 代替案と不採用理由

- 代替案A: 生き残りが 1 個でもあれば CI を落とす。
  - 不採用理由: relkb で見た生き残りの約半分は、文言の変化か結果の変わらない書き換えだった。落とすと、エージェントは help の文言を確かめるテストを書いて通そうとする。この決定で減らしたい、意味の無いテストを増やすことになる。
- 代替案B: PR ごとにリポジトリ全体にかける。
  - 不採用理由: relkb の規模でも、ラズパイでは 25 分で終わらなかった。PR と関係の無いモジュールの生き残りも並び、どれを直すべきかが分からなくなる。
- 代替案C: pre-commit に入れる。
  - 不採用理由: 重く、`--no-verify` で飛ばせる。
- 代替案D: 道具に cosmic-ray を使う。git の差分の行だけに絞る機能と、閾値で落とす機能がある。
  - 不採用理由: 対応する Python は 3.13 までで、3.14 の構文（括弧なしの `except A, B:`）を読めないという報告がある。
- 代替案E: 道具に pytest-gremlins を使う。pytest のプラグインで、テストの変更でキャッシュが消える。
  - 不採用理由: 2025-12 に作られたばかりで、変異の種類は 5 つしかない。mutmut は 2016 年からあり、2024-11 以降のコミットは 248 件、貢献者は 60 人いる。
- 代替案F: 変えた行だけに絞る（Google のやり方）。
  - 不採用理由: mutmut には行で絞る機能が無く、名前で絞れるのはモジュール・関数の単位まで。モジュールの単位なら、名前のパターンを並べるだけで済む。触ったモジュールの前からある生き残りも出るが、落とさないので PR は止まらない。

## 4. 影響

- コードへの影響: `pyproject.toml`（dev 依存・`[tool.mutmut]`・mypy の `exclude`）、`.gitignore`、`.github/workflows/ci.yml`。既存のプロジェクトがテンプレートの更新を取り込むと、次の PR から、触ったモジュールの前からある生き残りもコメントに出る。
- 運用への影響: `mutation` ジョブには `pull-requests: write` が要る。fork からの PR はトークンが読み取り専用でコメントを書けないため、ジョブの条件で外す。mutmut は fork を使うので Windows では動かない（WSL なら動く）。テストを変えても mutmut の前回の結果は消えないので、手元で流す前に `mutants/` を消す（mutmut の issue #626）。CI は毎回まっさらな状態から流すので、この問題は起きない。
- ドキュメントへの影響: `project/AGENTS.md`（テストの節）、`project/README.md.jinja`（よく使うコマンド）、PR テンプレートのチェックリスト、根の `README.md`。

## 5. フォローアップ

- 生き残りのうち直さなくてよいものの割合を、生成先の PR のコメントで数える。文言の変化が多ければ、mutmut の設定で文字列の変異を外せないかを調べる。
- 1 回の PR で変えたモジュールが多く、ジョブが 10 分を超えるようなら、関数の単位に絞る（`tools/code_graph.py` が出す「変わった定義」を使う）。

## 6. 変更履歴

- 2026-11-25: 初版作成。
- 2026-11-25: 変異を入れる範囲（変えたモジュール）は、[ADR 0011](./0011-mutation-testing-on-changed-functions.md) で、中身を変えた関数・メソッドに置き換えた（5 節のフォローアップの 2 つ目を実行した。代替案 F の「モジュールの単位なら済む」は、実測で成り立たなかった）。時間の上限とコメントに出す数も 0011 で足した。mutmut を使うこと、生き残りで CI を落とさないこと、テストの規約は変えていない。
