# ADR 0007: PR ごとにコードの関係の差分をレビューする人に出し、関数の複雑さを CI で止める

最終更新: 2026-11-14
- ステータス: 承認済み(accepted)
- 決定者: shogo-hs
- 関連: [ADR 0003](./0003-expand-ci-quality-gates.md), [ADR 0005](./0005-code-as-design-source-of-truth.md)

## 1. 文脈

- 実装の多くを AI のエージェントが書くようになり、速さと引き換えに、人がコードの中身と関係を追えなくなる。実測の報告では次のことが起きている。
  - Cursor を入れた 806 リポジトリで、関数の複雑さが +41%、静的解析の警告が +30% になった（arXiv 2511.04427、2025-11）。
  - AI と共著の PR の 79.0% が、レビューもコメントも無しでマージされている（arXiv 2601.13754、2026-01）。PR の大きさは +154%、レビュー時間は +91%（Faros、2025-07、相関のみ）。
  - AI を使って書いた人は、直後の理解のテストで 50%、手で書いた人は 67%（Anthropic の RCT、2026-01、52 人）。
- [ADR 0005](./0005-code-as-design-source-of-truth.md) で、コードと重複する文書（関係図を含む）は作らないと決めている。手で書いた関係図は、コードから離れていくため。
- エージェント向けには、関係グラフを見せても効果が出なかった。wsonto（約 5,000 行）で、課題 5 つ × 「編集の直後に呼び出し元の一覧を hook で差し込む／差し込まない」の 10 本を流し、合否は 10/10 で同じだった。ターン数の合計も 124 と 132 で、差は誤差の範囲だった。呼び出し元は grep で見つかり、壊れた箇所はテストが教えていた。

## 2. 決定

- CI に `code-graph` ジョブを足す。PR ごとに base と head の `src/` から、`tools/code_graph.py` で関係を毎回作り直し、その差分を PR にコメントする。同じ PR への 2 回目以降は前のコメントを上書きする。差分の中身は次の 4 つ。
  - 増えた・消えた定義（クラス・関数・メソッド）
  - 引数・戻り値・継承元が変わった定義
  - モジュールどうしの import の増減（Mermaid の図）
  - モジュールをまたぐ呼び出し・継承の増減
- グラフは保存せず、人もエージェントも書かない。関数を消せば差分に「消えた」と出て、足せば「増えた」と出る。誰かが更新を忘れる余地が無い。対象はモジュール直下とクラス直下の定義（`if` / `try` / `with` の中を含む）と、すべての import。構文エラーなどで読めないファイルは、コメントに名前を出して飛ばす。
- ruff に `C90`（McCabe の循環的複雑度）を足し、`max-complexity = 10` を超える関数があれば `ruff check` で落とす。品質ゲートの本数（6 本）は変わらない。
- 判断基準として、次の 3 つを優先した。エージェントの判断に頼らず必ず出ること。依存を増やさないこと（`tools/code_graph.py` は標準ライブラリだけで書いた）。実測で効果が無かったものは入れないこと。

## 3. 代替案と不採用理由

- 代替案A: CodeGraphContext や code-graph-rag などのコードグラフを、MCP でエージェントに見せる。
  - 不採用理由: 上の 10 本の実測で効果が出なかった。論文でも、grep で見つかる課題では差が無いか悪くなり、指示してもエージェントは 58% の試行でグラフのツールを呼ばなかった（CodeCompass、2026-02）。グラフ DB の運用も増える。
- 代替案B: relate（Neo4j Labs の組み込み型グラフ DB）にグラフを保存して問い合わせる。
  - 不採用理由: 差分を出すだけなら DB は要らない。relate は Labs の実験的な公開で、サポートが無い。
- 代替案C: 関数やクラスに `@feature("...")` のようなデコレーターを付け、機能の台帳を作る。
  - 不採用理由: 効果を測った例が見つからない。付け忘れは CI で検査できても、付けた機能名が正しいかは検査できず、意味がコードからずれていく。
- 代替案D: 生成したグラフのファイルをコミットする。
  - 不採用理由: マージのたびに衝突し、作り直し忘れでコードとずれる。
- 代替案E: pre-commit でグラフや差分を作る。
  - 不採用理由: `--no-verify` で飛ばせるので、必ず出る保証にならない。
- 代替案F: pylint の重複コード検出を品質ゲートに足す。
  - 不採用理由: 重複の増加は、上の 806 リポジトリの研究の本文では有意ではなかった。依存が 1 本増える。

## 4. 影響

- コードへの影響: `tools/__init__.py`・`tools/code_graph.py`・`tests/__init__.py`・`tests/tools/__init__.py`・`tests/tools/test_code_graph.py` を足す（`tests/__init__.py` が無いと、テストのパッケージ `tools` がテスト対象の `tools` を隠す）。既存のプロジェクトに当てると、複雑さが 10 を超える関数で `ruff check` が落ちる。まず分割し、分割できない関数だけ `# noqa: C901` を付けて理由を書く。
- 運用への影響: `code-graph` ジョブには `pull-requests: write` が要る。fork からの PR はトークンが読み取り専用でコメントを書けないため、ジョブの条件で外す。呼び出しは名前で解決する近似なので、変数や辞書に入れた関数、`from x import *` で入れた名前、関数の中で定義した関数は差分に出ない。同じ名前のモジュール（`x.py`）とパッケージ（`x/`）が並ぶと、定義の場所を取り違えることがある。PR の向き先のブランチだけを変えたときはジョブが走らない。
- ドキュメントへの影響: `python-uv-ci-setup` の SKILL.md・`templates.md`・`tooling-best-practices.md`、`README.md`、`AGENTS.md`、PR テンプレート。

## 5. フォローアップ

- [ ] テンプレートから立ち上げたプロジェクトの初回の PR で、`code-graph` ジョブが GitHub Actions 上でコメントを書けることを確かめる。
- [ ] レビューする人がコメントを読んで、PR の中身を説明できるようになったかを確かめる（人の理解への効果はまだ測っていない）。
- [ ] `max-complexity = 10` が実プロジェクトで厳しすぎないかを見直す。
