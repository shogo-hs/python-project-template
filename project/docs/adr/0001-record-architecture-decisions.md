# ADR 0001: ADR で設計判断を記録する

- ステータス: 承認済み(accepted)
- 決定者: このプロジェクトのチーム

## 1. 文脈

- 設計の正本はコードで、設計書は作らない（ADR 0002 で引き継いだ決まり）。コードからは「なぜそうしたか」と「採らなかった案」が読み取れない。
- チャットや PR の議論だけでは、後から採否の理由を探せない。

## 2. 決定

- 設計判断（アーキテクチャ、ツールの選択、運用の決まり）は `docs/adr/` に ADR として残す。
- 書き方は `.agents/skills/adr-management/SKILL.md` に従う。

## 3. 代替案と不採用理由

- 代替案A: PR の説明だけに残す。
  - 不採用理由: PR が増えると探せず、置き換えの関係も追えない。

## 4. 影響

- 設計判断を含む PR では、同じ PR で ADR を足す。

## 5. フォローアップ

- なし。
